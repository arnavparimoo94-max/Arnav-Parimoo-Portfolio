Purchase Order Extraction Pipeline

In production — actively evolving
B2B distribution · document parsing, data reconciliation, master-record design

The problem

Customers send purchase orders as PDF email attachments — one hospital chain per format, and every hospital lays its PDF out differently. Some don't even use table lines to separate items. Before this project, there was no central record of incoming orders at all: just a stream of emails someone had to open and read by hand, with no quick way to answer "what came in today," "what's still pending," or "what's been delivered."

How it works

Two simple parts, working together. The first part just watches the inbox: when a new order email arrives, it checks the sender is someone we actually expect orders from, saves the PDF attachment as-is, and adds it to a to-do list. It doesn't try to read what's inside the PDF — its only job is not missing an email.

The second part works through that to-do list: it opens each PDF, figures out which hospital sent it, reads the order details using rules built specifically for that hospital's layout, double-checks the numbers make sense, and then adds a clean row to one master spreadsheet that has every order in it.

These two parts are kept separate on purpose. The tool that watches the inbox is very good at reliably not missing emails, but it has no way to actually read a PDF's contents. Rather than trying to force one tool to do both jobs badly, each part does the one thing it's good at.

One constraint shaped every choice here: no budget was allocated for this outside normal operations, so every tool had to be free. Free-tier AI coding assistants for implementation, open-source libraries for reading PDFs, and the free scripting and spreadsheet tools already built into Google Workspace, rather than any paid API or third-party service.

Problems I caught — things only someone who knew the business would notice

  • The same product was being entered under different names. Different hospitals — and sometimes the same hospital — described the same item slightly differently on their PDFs. Without cleanup, the system would treat "IV Cannula 20G" and "Cannula, IV, 20 Gauge" as two different products, splitting one item's order history in two. This came to a head during a full reconciliation against the business's accounting records — 676 items checked against the product list, resulting in 210 new canonical products added and dozens of variants matched to the right one. That matching now feeds back into the system automatically for future orders.
  • We were at risk of accepting orders we can't actually fulfil. A hospital sometimes sends a PO for a product line we don't actually supply to them — sent in error, or meant for a different supplier. Left unchecked, that order would sit in our system looking like a real, expected order. Built a check that flags any hospital-and-product combination we're not actually authorized to fulfil, instead of silently accepting it.
  • The same hospital brand showing up as several different "hospitals" in the data. One hospital chain operates under a few different legal/billing names, and its site names on the PDFs weren't always real place names. Left alone, this would fragment one hospital's order history across several look-alike entries. Fixed by building one master list that maps every variant name to the one real hospital, using postal-code lookups to confirm the real location where needed.
  • A duplicate-flagging screen that looked fine but didn't actually work. The first version let someone mark two products as "same" with a simple yes/no per row. Testing it against a real case broke it immediately — three items were the same product, one was different, and yes/no per row simply can't express that. Rebuilt so items are compared and grouped in pairs instead.

Problems the system hit while running — the more technical fixes

  • One sender's emails kept "disappearing." An order from one specific hospital wasn't showing up when we searched for it — at first it looked like it simply hadn't arrived. It had arrived; the email search tool itself had a blind spot for that sender that no search phrasing could work around. This is the exact discovery that led to building the separate inbox-watcher described above, instead of relying on a general search feature to find new orders.
  • The tool we planned to use for reading PDFs wasn't available. The library originally picked for extracting text from PDFs couldn't even be installed in the environment the code runs in. Rebuilt the reading logic on a different tool, and had to work around that tool's own quirk of scrambling multi-column layouts by default.
  • Dates were silently getting corrupted. The spreadsheet software automatically converts anything that looks like a date into its own internal number format, which corrupted every date already stored — once, and then it crept back in four more times in different parts of the code because the fix was easy to forget. Now there's a standing rule: any code that writes a date must use the fix, no exceptions.
  • A number could silently lose a digit. One hospital's PDFs occasionally split a number's trailing digit onto a second line inside the same cell — so 200,000 could get read as 20,000, with nothing about it looking obviously wrong. Caught by comparing extracted totals against the source PDFs directly, not by anything that would have flagged itself.
  • The safety check meant to catch bad data had its own bug. The validation step that's supposed to block anything incorrect from being saved had a crash bug — a function being called with a setting it never actually accepted. It was only found by reading two parts of the code side by side, which meant that check may not have been working at all for a stretch of earlier runs. Fixed, and now tested directly rather than just assumed to work.
  • Order status was quietly resetting itself. Whenever an order got fully replaced with a corrected version, its delivery status silently reset to "Pending" even if it had already been marked delivered — a bug that had been running unnoticed for a while. Found and corrected across roughly 25 affected orders, and status updates now run every time, without exception, on every write.
  • A data-entry mistake that would have erased real decisions. Seventeen approval records had "Approved" typed into the wrong column — meaning the system's actual check would never have recognized them as approved. Worse, a newly built cleanup job would have quietly auto-archived every one of them as "no response," erasing decisions that had already genuinely been made. Caught before that cleanup job ran.
  • A recent outage, and a reminder this is still young. A few days ago, an email-service usage limit briefly took the inbox-watching layer offline before it recovered on its own. Not a design flaw so much as evidence the system is still being actively run, watched, and adjusted on real, current data — not a one-time build left untouched.

Rules the system always follows

  • If anything in a batch looks wrong, nothing in that batch gets saved — better to fix and re-run than to save half-correct data.
  • If the system isn't sure about something, it asks a person instead of guessing — an unclear match gets flagged for review, never silently resolved on its own.
  • Nothing gets permanently deleted automatically — old or rejected data gets moved aside, never erased, even when it would be easier to just delete it.

What's planned next

  • Extending this to a much larger volume of orders and hospitals. This is deliberately running first on the smaller of two related businesses under shared ownership, at today's scale — roughly ten hospital chains. The plan is to extend the same system to a second, significantly higher-volume business once it's proven here. Many of the lessons above — the entity-matching approach, the fail-closed validation, the data-corruption fixes — should transfer directly, but a meaningfully larger volume is expected to surface new edge cases this scale hasn't hit yet.
  • A way to enter orders that don't come by email. Not every order arrives as an email attachment — staff will get a simple screen to enter those directly, going into the exact same master record under the same checks, rather than a separate, less-reliable path.
  • Tracking what was actually delivered, not just what was ordered. Adding how much of each order was actually supplied, pulled from the business's existing accounting records. Still deciding whether that's a daily file import or a direct connection — depends on what the accounting software actually supports.
  • A simple reporting view. Once the order and delivery data is reliable, a straightforward daily/weekly/monthly summary — what came in, what's outstanding — instead of scrolling through the raw master table by hand.
  • Asking questions in plain English. The longer-term goal: connect an AI assistant to this same data so a question like "what's pending for this hospital" gets answered directly, instead of someone looking it up manually. This was the plan from the start — the clean, structured record above is the foundation it needs to work.

Outcome

One clean, central record of every order — 287 so far and growing — across ten hospital chains and roughly 267 canonical products, where before there was none. It runs on its own, catches the mistakes above automatically going forward, and more issues like these keep surfacing week to week as it's used on real data — which is expected for a system still this new, and each one gets fixed the same way: caught, understood, then made structurally impossible to repeat.

Automated Document Reconciliation for Compliance Claims

Live in production — v8.7
B2B distribution · OCR verification, execution-constrained scheduling

The problem

A monthly compliance obligation to a manufacturer partner required 600+ individual claims, each needing a matched pair of source documents — a tax invoice and a corresponding shipping document — as evidence. Before automation, this was fully manual: downloading, cross-referencing, and organizing documents by hand, consuming roughly one full person-day per cycle with no other work possible that day, and leaving real room for a mismatched cancelled/re-billed order to slip through undetected.

Architecture

A two-stage pipeline built to minimize the most expensive operation — OCR — while still catching what filename matching alone would miss. Stage 1 categorizes documents by filename convention alone: fast, free, no contents read. Stage 2 takes only the filename-matched pairs and OCR-verifies them, reading the actual document identifier inside each file and cross-checking it against its counterpart — catching the case where two files share a matching filename but disagree internally, which happens when an order is cancelled and re-billed under a new number while the original shipping document is reused.

No budget was allocated for this project — it ran entirely on free tools: free-tier AI coding assistants, the native scripting built into Google Workspace, and OCR through Google's own document tools rather than a paid extraction service.

Production problems solved

  • Platform execution timeout. The environment enforced a hard 6-minute execution ceiling; a large batch risked being killed mid-run with no report sent. Fixed with a self-imposed 315-second internal cutoff, checked before starting each new item — a 45-second buffer that guarantees the run always finishes and reports cleanly.
  • OCR quota exposure. A second, independent guardrail alongside the time cutoff: a hard cap on documents processed per run, regardless of remaining time — bounding OCR calls (the most quota-sensitive step) so a fast run can't silently exhaust API quota.
  • Financial-year rollover causing false matches. Document numbers reset every fiscal year, so a number alone isn't a stable identifier — the same number can exist in two different years and refer to unrelated documents. Fixed by embedding fiscal year explicitly into the matching key, so a pair can never cross a fiscal-year boundary by accident.
  • Alert fatigue from transient errors. Non-critical alerts are suppressed outside a defined local-time window and logged instead; genuinely critical, action-required errors always bypass this and fire immediately.

Outcome

Running in production at v8.7, saving roughly one day of manual work per monthly cycle, processing invoice/shipping-document pairs in the low hundreds against a 600+/month claims volume.
